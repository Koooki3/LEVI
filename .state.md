# LEVI workspace (`.state`) reference

What lives under `LEVI_WORKSPACE` (default `.state/` at the repo root), how it's named, what's safe to delete, and how the two different "converted dataset" concepts relate. Read alongside [`docs/CONVERSION.md`](docs/CONVERSION.md) (raw-capture conversion) and [`docs/SAM3.md`](docs/SAM3.md) (object-annotation sidecar).

## Layout

All paths are relative to `LEVI_WORKSPACE` (`levi/paths.py`).

| Path | Contents | Cleanup |
| --- | --- | --- |
| `<dataset-name>/` | Any registered dataset — a raw capture tree, or a converted/registered LeRobot dataset — flat, directly under the workspace root. No wrapping subfolder. | **Protected.** `levi maintenance clean` never touches it. |
| `levi_<job-id>/` | A conversion job's default output (when no custom `--output`/output field is given): `capture/` (staged copy) + optional `filtered/` + `dataset/` (the actual LeRobot output) + `preflight.json` + `validation.json`. Flat under the workspace root, same as any other dataset — **not** nested under a `datasets/` subfolder. | **Protected**, but **not auto-pruned** — see [Known gap](#known-gap-stale-job-outputs). |
| `outputs/LEVI/workbench/` | LEVI's own annotation layer: `annotations/` (language/event, keyed by dataset name, no hash), `object_annotations/` (SAM3, same convention), `diagnostics/` (reports, hash-suffixed), `reviews/`, `jobs/` (job metadata/logs/results), `datasets.json` (the catalog registry). | Protected. |
| `outputs/LEVI/exports/` | Annotated-dataset exports (see [Product 2](#product-2-registered-dataset--annotated-training-dataset)), named `{dataset-name}_annotated_{hash}`; re-exporting the same source dataset reuses the same directory. | Protected. |
| `checkpoints/` | SAM3 model weights. | Protected. |
| `.cache/`, `tmp/` | HF Hub download cache, build/test temp files. | `levi maintenance clean` covers this. |

### Naming convention

Two different rules, both keyed off the dataset's own identity (see `DatasetState._identity_hash` / `dataset_display_slug` in `backend/app.py`):

- **Live, shared sidecars** (`annotations/`, `object_annotations/`) use the **bare dataset name, no hash**. Several LEVI processes on the same host (different collaborators, or one person on two ports) must resolve the same dataset name to the exact same directory, so their edits land in the same files and stay in sync. Trade-off: two genuinely different local datasets sharing a folder basename would collide here — keep dataset folder names distinct.
- **Snapshot-style artifacts** (`exports/`, `diagnostics/`) use `{name}_{short-hash}`. These are point-in-time copies/reports where two different sources sharing a display name must *not* silently overwrite each other.

Conversion job outputs (`levi_<job-id>/`) use neither — the job ID (timestamp + random suffix) is already unique, and the folder is disposable/auditable per run rather than a live shared sidecar.

### Known gap: stale job outputs

`levi/maintenance.py`'s cleanup allowlist is intentionally narrow — build/dev caches only (`.next/cache`, `__pycache__`, `.ruff_cache`, the HF download cache, pinned Bun installers). It deliberately excludes every dataset-shaped directory, `levi_<job-id>/` included, because a cleanup tool must never guess whether something is disposable test output or real, valuable data.

The cost: an abandoned, half-finished, or superseded conversion run has no automatic pruning path and accumulates until someone looks. A reasonable half-measure, not yet implemented: let cleanup remove `levi_<job-id>/` directories whose `validation.json` reports `"ok": false` or is missing entirely (i.e., provably failed or incomplete, never a "real" dataset in the first place) — succeeded runs would still need a human decision.

## Two different "converted dataset" concepts

LEVI has two independent conversion/export paths that produce different things — easy to conflate.

### Product 1: raw capture → LeRobot dataset (`levi/conversion/`)

- Always **v2.1** output (the built-in converter never emits v3.x).
- Path: `{job output}/dataset/`, alongside `capture/` (staged copy), optional `filtered/` (after static-frame filtering), `preflight.json`, `validation.json`.
- `dataset/` structure: `meta/info.json`, `meta/episodes.jsonl` (see `levi_outcome` below), `meta/episodes_stats.jsonl`, `meta/tasks.jsonl`, `meta/stats.json`, `meta/levi_provenance.jsonl` (maps episodes back to source demos), `meta/levi_conversion.json` (records the options used), `data/chunk-000/episode_*.parquet` (7-dim action/state: xyz + euler/quaternion + gripper), `videos/chunk-000/{observation.images.hand,observation.images.view1}/episode_*.mp4`.

### Product 2: registered dataset → annotated training dataset (`backend/app.py:_do_export`)

- Input is **any** registered LeRobot dataset — LEVI-converted, externally converted, or downloaded from the Hub.
- Path: `outputs/LEVI/exports/{dataset-name}_annotated_{hash}/`; re-exporting the same source reuses the same directory rather than piling up copies.
- Structure: `meta/` (rewritten — adds `language_persistent`/`language_events` features and the `say` tool schema), `data/*.parquet` (rewritten with the annotation columns baked in), `videos/` (hardlinked/copied, skipped on reuse since source captures are immutable), `annotations/language/episode_*.json` + `manifest.json` (human-readable, write-only audit mirror — LEVI never reads it back), `annotations/sam3/` (SAM3 sidecar snapshot, if any object annotations exist).

## Supported raw capture formats

Three formats the built-in converter (`levi/conversion/`) understands, two of them in active use.

### Type 1 — teleoperation capture (e.g. `data_collection_robotiq`)

**Format**: a `demo_NNNN/` folder with `end_effector_pose.csv`, `gripper_state.csv`, `events.csv`, `metadata.json`, `wrist_camera.mp4`/`side_camera.mp4` (or `<camera>_raw.avi`); `task_description.txt` one level up, shared by every demo under that task. `success_flag` sits at its default `0` in practice (an operator-toggled "keeper" flag rarely pressed); no `data_source` field; a camera stall is the flat `metadata.json["camera_stalled"]` boolean; the terminal `events.csv` row is `stop_demo`.

**Pipeline**: `uv run levi convert pipeline --source <capture dir> --output <dir>` (or the workbench page) → staged copy → FPS normalization (auto-detects and lowers the target FPS to the batch's measured rate when the request exceeds it — real rigs commonly run a little under their nominal rate) → preflight (`stage-preview`) → optional static-frame filter (on by default) → v2.1 conversion → full `validate`.

**Output**: Product 1, above. No `levi_outcome` (meaningless for teleoperation data).

**LEVI features available**: full episode browsing, Statistics/Filtering/Frame gallery, Action Insights (full dataset / range / by task), Doctor diagnostics, language/event + SAM3 object annotation, review flagging + export, "export annotated dataset" for training.

### Type 2 — policy-rollout / online-RL eval capture (e.g. `online_rollout_data`)

**Format**: identical CSV/video layer to Type 1, plus `metadata.json["data_source"] == "policy_rollout"` and an `eval` block (`outcome`, `checkpoint_dir`, `steps`, …). `success_flag` is the real task outcome (0/1, matching `eval.outcome`); a camera stall is the nested list `metadata.json["cameras"]["stall_detection"]["stalled"]`; the terminal event is `episode_end`.

**Pipeline**: identical command/UI to Type 1 — `data_source` is detected automatically, no extra configuration.

**Output**: Product 1, with `meta/episodes.jsonl` additionally carrying `levi_outcome: "success" | "failure"` per episode.

**LEVI features available**: everything Type 1 has, plus a success/failure dot per episode in the sidebar and a "Failures · N" filter (single-task datasets, typical for eval captures, correctly hide the task filter rather than erroring).

Verified end-to-end against a real batch: the `pick_screws_of_same_size_into_the_empty_slot_of_screw_box` eval task, 171 demos, 124 failure / 47 success, converted with plain default options (FPS auto-adjusted from the requested 10 to the measured 9.395653).

### Type 3 — image-sequence capture

**Format**: `wrist_camera/`/`side_camera/` as directories of naturally-sorted PNG/JPEG instead of `.mp4`; `source_fps` must be set explicitly (nothing to probe).

**Status**: supported by the code (used internally by the `images` stage's own output), but neither real corpus above uses it. Ready if a frame-sequence capture ever shows up.

### Already-converted LeRobot datasets

Not a "raw" format, but relevant: LEVI can register and fully use **any** v2.0/v2.1/v3.0/v3.1 dataset directly — regardless of what produced it (LEVI's own converter, an external script, or a Hub download) — with no conversion step. `lerobot_fr3_filtered_robotiq_v3` is exactly this case: converted by an external script (`data_collection_robotiq/scripts/raw2lerobot.py`), not by LEVI.
